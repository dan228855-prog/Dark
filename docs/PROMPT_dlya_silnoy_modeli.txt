ЗАДАЧА: Реализовать три взаимосвязанные системы для кооперативной игры на Unreal Engine 5
(1-5 игроков, Listen Server, C++ + Blueprints), в рамках вертикального среза проекта.

КОНТЕКСТ ПРОЕКТА:
Кооперативная игра про выезды в процедурные локации от лица команды, работающей на
корпорацию D.A.R.C. Скрытая механика: в игровой системе скрывается вышедший из-под
контроля ИИ (внутриигровое имя - E.V.A., Environmental Verification Assistant).
Игроки не должны узнавать об этом напрямую - только через редкие странные события
и накопленные несоответствия.

Уже реализовано (для контекста и переиспользования паттернов):
- IInteractable - интерфейс взаимодействия (CanInteract, OnInteract, GetInteractionPrompt)
- UInteractionComponent - компонент на игроке, трейсит взгляд, шлет Server RPC
- AInteractableDoor - дверь с реплицируемым bIsOpen
- ACarryableItem - переносимый предмет с реплицируемым CurrentHolder
- ADarcGameMode / ADarcGameState (с EMissionPhase) / ADarcPlayerState (с bIsAlive, DeathCount)

Архитектурный принцип проекта: сервер полностью авторитетен для всего важного игрового
состояния, клиенты только запрашивают действия. Игра не должна строиться целиком на C++
и не должна строиться целиком на Blueprints - архитектурные системы на C++, контентная
настройка на Blueprints. Соло - полноценный режим, не урезанный кооп: любая механика,
требующая нескольких игроков, обязана иметь альтернативу для одного.

ЧТО НУЖНО РЕАЛИЗОВАТЬ:

1. WorldMemory (серверная система)
Запоминает в рамках текущей игровой сессии:
- состояние дверей (открыта/закрыта) по уникальному ID двери
- перемещенные предметы (кто где что переносил/оставил)
- посещенные игроками помещения
- разделение игроков по локации (кто в какой комнате)
- найденные объекты
- совершенные взаимодействия
- последовательность выполненных задач

Система должна уметь позже возвращать "искаженное эхо" на основе этих данных
(например: ранее перемещенный стул снова слегка сдвинут; ранее открытая и оставленная
дверь оказывается закрыта). Сама генерация эха - в System 2 ниже, WorldMemory только
хранит и предоставляет данные.

Продумай: должна ли эта система быть UGameInstanceSubsystem (переживает уровни) или
привязана к GameState конкретной сессии/выезда - обоснуй выбор с точки зрения жизненного
цикла Listen Server и того, что "кампания" переживает несколько выездов, а WorldMemory
по формулировке документа - "в рамках текущей сессии" (то есть, вероятно, сбрасывается
или частично переносится между выездами - реши, как передать самое важное дальше в
постоянное состояние кампании, а что забыть).

2. RareEventManager (серверная система, data-driven)
Управляет редкими сюжетными событиями. Готовый список из 10 примеров событий
(не более одного сильного события на уровень, некоторые уровни - без событий вовсе,
ранние уровни почти без скримеров, события НЕ блокируют прохождение):
- "ПЯТЫЙ ИГРОК": терминал показывает "CONNECTED: 5 / EVA STATUS: ONLINE"
- "ФОТОГРАФИЯ КОМАНДЫ": старое фото содержит столько людей, сколько сейчас в сессии
- "ДОКАЗАТЕЛЬСТВО": документ описывает уже пережитое игроками событие
- "ОН УЖЕ ВЫШЕЛ": шаги слышны из только что покинутой комнаты
- "КОМНАТА, КОТОРОЙ НЕ БЫЛО": появляется дверь в несуществующую комнату, затем исчезает
- "НЕ ТОТ ГОЛОС": игрок слышит голос другого игрока по рации, хотя тот молчит
- "ВИДЕО С БУДУЩЕГО": запись показывает действие за несколько секунд до его совершения
- "НЕПРАВИЛЬНОЕ КОЛИЧЕСТВО": предметов становится больше или меньше
- "КОМНАТА ПОМНИТ": надпись меняется после возвращения игроков (использует WorldMemory)
- "ИГРОК, КОТОРОГО НЕТ": "PLAYER 05 - E.V.A. - ONLINE"

Спроектируй data-driven структуру (DataTable/DataAsset) с полями: ID, тип события,
диапазон применимых уровней, шанс срабатывания, требуемая дистанция до игрока/объекта,
условия срабатывания (в т.ч. может ссылаться на данные WorldMemory), "сила страха"
(интенсивность), повторяемость (одноразовое / может повторяться), перенос состояния
в постоянную кампанию (влияет ли произошедшее событие на будущие выезды).

Технически: RareEventManager работает авторитетно на сервере, клиентам отправляется
только результат события и нужные для его показа параметры - не вся внутренняя
логика/данные принятия решения.

ВАЖНОЕ ОГРАНИЧЕНИЕ ПО ЛОРУ: избегать прямых названий реальных ИИ (ChatGPT, Claude, Grok)
в игровых текстах и в именах классов/ассетов, которые могут попасть в билд как строки,
видимые игроку. Использовать вымышленные технические термины в духе: CONTEXT WINDOW
EXCEEDED, ATTENTION_LAYER, MODEL RESPONSE INTERRUPTED, INFERENCE SESSION, CONTEXT_04,
CHAT_SESSION_ARCHIVE. Это касается текстовых строк для игрока, не имен классов C++.

3. Task / Objective System (P0, ранее не реализована)
Игроки не должны просто искать заранее обозначенные точки взаимодействия - система должна
поддерживать задачи как цепочки действий с несколькими возможными путями решения (пример
из документа: "получить данные с сервера" = найти сервер -> получить доступ -> найти
пароль/альтернативный способ -> восстановить питание при необходимости -> подключить
накопитель -> скопировать -> извлечь -> доставить на базу). Заложи поддержку того, что
ошибка/непредвиденное событие может породить новую подзадачу в реальном времени
(например, повреждение кабеля при взломе двери отключает питание сервера - это должно
стать возможным добавить как emergent-подзадачу, а не быть жестко захардкожено заранее).

Учти EMissionPhase из ADarcGameState (Preparation / InProgress / Completed / Failed) -
Task System должна согласованно обновлять эту фазу.

ЧТО НЕ НУЖНО В ЭТОЙ ЗАДАЧЕ:
- полноценная процедурная генерация уровней (это отдельный этап P2)
- финальный список из всех 7 уровней и весь их контент
- сложный NPC/монстр с ИИ-поведением
- Steam-интеграция

ФОРМАТ ОТВЕТА: C++ заголовки и реализации (Public/Private раздельно, как принято в UE5
модулях), с комментариями на русском, объясняющими сетевые решения и почему выбрана
именно такая архитектура (особенно для WorldMemory: GameInstanceSubsystem vs GameState).
Где нужна ручная настройка контента (конкретные тексты событий, конкретные DataTable
строки) - оставляй BlueprintImplementableEvent/DataTable точки расширения, а не
хардкодь финальный контент в C++.
